================================================================================
  SECTION 2: DOMAIN BACKGROUND
================================================================================

  2.1  WHAT IS FOG COMPUTING?
  ────────────────────────────
  Fog Computing is a distributed computing paradigm that extends cloud
  services to the edge of the network. Instead of sending all data to a
  distant cloud data centre, computation is performed on nearby "fog nodes"
  — small edge servers located close to the data source.

  Why Fog over Cloud for Healthcare?
    - LATENCY:  A surgery monitoring system cannot wait 100+ ms for a cloud
      response. Fog nodes are physically nearby (same building/campus),
      reducing round-trip time to single-digit milliseconds.
    - BANDWIDTH: Streaming high-resolution medical data to the cloud
      saturates network links. Fog processes data locally.
    - RELIABILITY: Internet outages don't affect local fog processing.
    - PRIVACY: Sensitive patient data stays within the hospital network.

  2.2  WHAT IS IoT IN THIS CONTEXT?
  ──────────────────────────────────
  IoT (Internet of Things) refers to the network of connected medical
  devices in a smart hospital:
    - Patient monitors (heart rate, SpO2, blood pressure)
    - Surgical equipment (robotic arms, imaging systems)
    - Diagnostic devices (X-ray machines, MRI scanners)
    - Environmental sensors (room temperature, air quality)

  These devices generate COMPUTATIONAL TASKS — data that needs to be
  processed (analysed, classified, stored) in real time.

  2.3  THE TASK OFFLOADING PROBLEM
  ────────────────────────────────
  Task offloading = deciding WHICH fog node should process WHICH task.

  Constraints:
    - Each task has a DEADLINE (e.g., surgery data must be processed within
      15-22 seconds)
    - Each fog node has LIMITED CAPACITY (measured in VRUs — Virtual
      Resource Units)
    - Network bandwidth is shared (uplink/downlink = 20 MHz = 2500 KB/s)
    - Not all tasks are equally important — a major surgery matters more
      than a routine checkup

  If a task cannot be assigned to ANY fog node → OUTAGE.
  In healthcare, outages for critical operations are unacceptable.

  2.4  MATCHING THEORY — WHY NOT JUST LOAD BALANCE?
  ──────────────────────────────────────────────────
  Standard load balancing optimises for a single metric (throughput or
  latency). The task offloading problem is a MULTI-CRITERIA MATCHING
  problem:
    - Tasks have preferences over fog nodes (based on delay + energy)
    - Fog nodes have preferences over tasks (based on urgency)
    - Both sides have constraints (deadlines, quotas)

  This is analogous to the HOSPITAL-RESIDENT MATCHING problem (solved by
  the Gale-Shapley Deferred Acceptance algorithm). MSDA extends DA with
  multi-stage quota enforcement for fairness.

================================================================================
  SECTION 4: BASE PAPERS
================================================================================

  4.1  PRIMARY BASE PAPER — M-DAFTO
  ──────────────────────────────────
  Title:   "M-DAFTO: Multi-Stage Deferred Acceptance Based Fair Task
            Offloading in IoT-Fog Systems"
  Source:  IEEE Journal of Internet of Things (JIOT), 2022
  DOI:     10.1109/JIOT.2022.3183979

  What M-DAFTO Does:
    - Proposes a Multi-Stage Deferred Acceptance (MSDA) algorithm for
      assigning IoT tasks to fog nodes.
    - Uses a 2-criteria urgency function:
        U = w1 × 1/(Deadline − Delay) + w2 × 1/pref(Ti)
    - Generates weights using a 2×2 AHP matrix (always consistent).
    - Normalises delay only (no energy).
    - Treats ALL tasks in a single undifferentiated pool.
    - Uses min-quota and max-quota enforcement for fairness.
    - Implements Algorithm 9 (Single-Type MSDA) with deadline-based
      status flag (true = enforce deadline, false = relax for min quotas).

  What M-DAFTO Does NOT Do:
    - Does NOT differentiate between critical and routine tasks.
    - Does NOT consider energy consumption in urgency scoring.
    - Does NOT have separate quota tracking for different task types.
    - Does NOT produce separate preference rankings by task severity.

  4.2  SECONDARY REFERENCE — 2-Type MSDA Theory (Oomori & Manabe)
  ────────────────────────────────────────────────
  File:    base-2type-msda.pdf (Oomori & Manabe, 2026)
  
  This paper provides the theoretical foundation for extending MSDA to
  handle two types of agents (R-type and S-type) with separate quota
  constraints. It defines Algorithm 10 (2-Type MSDA) which maintains:
    - p_c  = minimum quota (all tasks) for fog node c
    - q_c  = maximum quota (all tasks) for fog node c
    - pr_c = minimum quota (R-type/Major tasks) for fog node c
    - qr_c = maximum quota (R-type/Major tasks) for fog node c

  This algorithm is the basis for the proposed system's core matching logic.


================================================================================
  SECTION 5: LIMITATIONS OF THE BASE PAPER (M-DAFTO)
================================================================================

  1. SINGLE-POOL MATCHING
     All tasks compete in one undifferentiated pool. A routine checkup
     competes for the same fog node slots as a critical surgery. Under high
     load, critical tasks can be starved of resources.

  2. 2-CRITERIA URGENCY ONLY
     The urgency function uses only delay difference and preference count.
     Energy consumption — a key concern in battery-powered IoT devices —
     is completely ignored.

  3. NO SEVERITY AWARENESS
     There is no concept of task severity (Major vs Minor). The algorithm
     cannot prioritise critical healthcare operations over routine ones.

  4. 2×2 AHP (TRIVIALLY CONSISTENT)
     With only 2 criteria, the AHP matrix is 2×2 and ALWAYS passes the
     consistency check (CR = 0 by definition). No actual validation occurs.

  5. DELAY-ONLY NORMALIZATION
     Only delay is normalised via Min-Max scaling. Energy is not normalised,
     not combined, and not used in preference ordering.

  6. SINGLE PREFERENCE LIST PER FOG NODE
     Each fog node has one preference ranking over ALL tasks. There are no
     separate rankings for different task types.


================================================================================
  SECTION 6: PROPOSED SOLUTION — WHAT THIS PROJECT CHANGES
================================================================================

  6.1  TECHNICAL CONTRIBUTIONS (8 total)
  ──────────────────────────────────────

  CONTRIBUTION 1: TWO-TYPE TASK CLASSIFICATION
    - Applied the R-type/S-type framework from Oomori & Manabe by mapping
      healthcare task severity: Major (critical operations like
      surgeries) → R-type, Minor (routine tasks like checkups) → S-type.
    - Assigned 50/50 randomly during task generation.
    - Following the 2-Type MSDA framework (Oomori & Manabe), Major tasks
      receive separate minimum quotas (pr_c), maximum quotas (qr_c),
      and separate fog-side preference rankings.
    - Ensures critical healthcare operations are NEVER starved of resources.

  CONTRIBUTION 2: TWO-TYPE MSDA MATCHING ALGORITHM
    - Adapted the 2-Type MSDA (Algorithm 10) from Oomori & Manabe that
      maintains separate quota tracking for Major (R-type) and Minor
      (S-type) tasks WITHIN the same multi-stage deferred acceptance
      framework.
    - Uses the "Modified DA" (runModifiedDA) from their framework which
      simultaneously enforces THREE constraints per fog node:
        (a) qr_c — maximum Major task quota
        (b) q_c − pr_c — maximum Minor task quota
        (c) q_c — total capacity limit
    - In the final stage, handles three cases (as defined in Oomori & Manabe):
        (a) Exact R-type count → DA for R-types + Single-Type MSDA for S
        (b) Exact S-type count → DA for S-types + Single-Type MSDA for R
        (c) Otherwise → Recursive 2-Type MSDA
    - Prevents "Major task starvation" that happens in M-DAFTO's single pool.

  CONTRIBUTION 3: ENERGY CONSUMPTION AS A METRIC
    - Extended urgency from 2 to 4 criteria by adding an energy term.
    - Energy is computed as:
        E = (TxPower × TxTime) + (ExecPower × ExecTime) + (RxPower × RxTime)
    - The inverse (1/Energy) is used in the urgency formula, so tasks with
      lower energy consumption at a particular fog node get higher urgency.

  CONTRIBUTION 4: SEVERITY SCORE IN URGENCY (γ FACTOR)
    - Added a severity multiplier γ(Ti) to the urgency formula:
        γ = 1.5 for Major tasks (formula: 1 + 1 × 0.5, where c=1, α=0.5)
        γ = 1.0 for Minor tasks (formula: 1 + 0 × 0.5, where c=0, α=0.5)
    - This naturally pushes Major tasks higher in fog node preference lists.

  CONTRIBUTION 5: SEVERITY-WEIGHTED NORMALIZATION
    - M-DAFTO uses plain Min-Max normalisation on delay only.
    - Proposed system normalises BOTH delay and energy using Min-Max.
    - Applies severity-based weight reduction:
        Minor tasks → weight = 0.5 on normalised values
        Major tasks → weight = 1.0 on normalised values
    - This means Minor tasks generate lower normSum values, leading to
      different fog node preference orders compared to Major tasks.

  CONTRIBUTION 6: 4×4 AHP INSTEAD OF 2×2
    - M-DAFTO uses a 2×2 AHP matrix (always consistent by definition).
    - Proposed uses a 4×4 AHP matrix with full consistency checking.
    - Consistency validation: CR ≤ 0.1 (using RI = 0.90 for n=4).
    - If CR > 0.1, the matrix is regenerated (up to 100 attempts).

  CONTRIBUTION 7: SEPARATE MAJOR/MINOR PREFERENCE LISTS & PRECEDENCE LISTS
    - As structurally required by the 2-Type MSDA framework (Oomori & Manabe),
      implemented separate fog-side preference rankings for:
        (a) All tasks (rankAllTasksPerFog)
        (b) Major tasks only (rankMajorTasksPerFog)
        (c) Minor tasks only (rankMinorTasksPerFog)
    - Builds separate deadline-sorted precedence lists for each type.
    - These feed into the 2-Type MSDA so each type is handled with its
      own priority ordering.

  CONTRIBUTION 8: GREEDY PLACEMENT METHOD (GPM) AS ADDITIONAL BASELINE
    - Added a third comparison algorithm (GPM) that assigns tasks greedily
      to fog nodes sorted by capacity, with no fairness or urgency.
    - Provides a lower-bound comparison point.
    - Reuses proposed normalisation/weights for fair metric evaluation.

  6.2  SUMMARY: BASELINE vs PROPOSED
  ───────────────────────────────────
  Feature                   Baseline (M-DAFTO)          Proposed System (Adapted 2-Type MSDA)
  ─────────────────────────────────────────────────────────────────────────────
  Task Types                Single pool                 Major vs Minor w/ quotas

================================================================================
  SECTION 7: KEY CONCEPTS & TERMINOLOGY
================================================================================

  7.1  DEFERRED ACCEPTANCE (DA) — Gale-Shapley Algorithm
  ──────────────────────────────────────────────────────
  A matching algorithm where one side (tasks) "proposes" to the other side
  (fog nodes). Each fog node tentatively accepts the best proposals up to
  its capacity and rejects the rest. Rejected tasks propose to their next
  choice. This continues until no more proposals can be made.
  DA guarantees a STABLE matching — no task-fog pair would both prefer
  each other over their current match.

  7.2  MULTI-STAGE DEFERRED ACCEPTANCE (MSDA)
  ───────────────────────────────────────────
  Extension of DA that handles MINIMUM QUOTAS (fairness).
  Standard DA can leave some fog nodes empty while overloading others.
  MSDA runs DA in multiple stages:
    Stage 1: Remove the "bottom" tasks (latest deadlines) from the pool.
             Run DA with remaining tasks using max quotas.
    Stage 2: Remove more bottom tasks. Run DA again.
    ...
    Final Stage: Use min quotas to force remaining tasks onto fog nodes,
                 even if deadlines are violated (relaxation).
  This ensures every fog node gets at least its minimum quota of tasks.

  7.3  2-TYPE MSDA
  ────────────────
  Extension of MSDA that tracks two task types (R-type = Major, S-type = Minor)
  with separate quota constraints. Uses a "Modified DA" with three-constraint
  rejection: Major quota limit, Minor quota limit, total capacity limit.

  7.4  AHP (ANALYTIC HIERARCHY PROCESS)
  ─────────────────────────────────────
  A multi-criteria decision-making method developed by Thomas Saaty.
  Steps:
    1. Define criteria (delay diff, pref count, energy, severity)
    2. Build a pairwise comparison matrix (P) using Saaty's 1-9 scale
    3. Compute weights by column-normalising P and row-averaging
    4. Validate consistency: CR = CI / RI ≤ 0.1

  Saaty Scale:
    1 = equally important, 3 = moderately more, 5 = strongly more,
    7 = very strongly more, 9 = extremely more.
    Even numbers (2,4,6,8) are intermediate values.

  7.5  VRU (VIRTUAL RESOURCE UNIT)
  ────────────────────────────────
  A logical unit of compute capacity on a fog node.
  VRU Capacity = (Total CPU in GHz × 1000) / Number of VRUs
  Example: 8 GHz → 8000 Mcycles/s ÷ 400 VRUs = 20 Mcycles/s per VRU
  A fog node with 400 VRUs can theoretically handle 400 concurrent tasks.
  Maximum quota = numberOfVRUs (hard capacity limit).

  7.6  QUOTAS
  ──────────
  Minimum Quota (p_c): The LEAST number of tasks fog node c must accept.
    Computed proportionally based on VRU capacity relative to the most
    efficient node (QuotaDeterminator.java).
  Maximum Quota (q_c): The MOST tasks fog node c can accept (= numberOfVRUs).
  For Major tasks: pr_c (min Major quota), qr_c (max Major quota).

  7.7  OUTAGE
  ──────────
  A task that could not be matched to ANY fog node = outage.
  Outage Rate = (unmatched tasks / total tasks) × 100%.
  In healthcare, Major outages are critical safety failures.

  7.8  TASK SATISFACTION (Eq. 20 from base paper)
  ───────────────────────────────────────────────
  For each matched task assigned to fog f:
    1. Build list of "acceptable" fogs (where delay ≤ deadline),
       ordered by the task's preferred fog indices
    2. K = number of acceptable fogs
    3. pos = position of f in the acceptable list (0-indexed)
    4. satisfaction = ((K − pos) / K) × 100
  Average across all tasks → avgTaskSat (0-100%).

  If a task gets its MOST preferred fog → satisfaction = 100%.
  If it gets its LEAST preferred → satisfaction = 100/K %.

  7.9  FN SATISFACTION (Eq. 21-22 from base paper)
  ────────────────────────────────────────────────
  For each fog node j:
    For each task assigned to fog j:
      1. Find rank of that task in fog j's ALL-tasks preference list
      2. satisfaction = ((prefListSize − rank + 1) / prefListSize) × 100
    sumSat = sum of satisfactions for all tasks assigned to j
    divisor = min(numberOfVRUs, prefListSize)
    fnSat_j = sumSat / divisor
  Average across all fog nodes → avgFnSat (0-100%).

  7.10  FAIRNESS INDICES
  ─────────────────────
  Gini Index (0 = perfectly fair, 1 = maximally unfair):
    Measures inequality in how tasks are distributed across fog nodes.
    Formula: sumDiff / (2 × N² × mean)
    where sumDiff = sum of |matchesPerFog[a] − matchesPerFog[b]| over all pairs.

  Jain Fairness Index (0 = unfair, 1 = perfectly fair):
    Formula: (Σ matchesPerFog)² / (N × Σ matchesPerFog²)
    A Jain index close to 1.0 means all fog nodes get roughly equal load.


================================================================================
  SECTION 8: MATHEMATICAL FORMULATIONS
================================================================================

  NOTE: The per-step formulas are in project_flow.txt. This section
  provides a consolidated reference of ALL formulas used.

  8.1  OFFLOADING DELAY
  ─────────────────────
  For task i offloaded to fog node j:
    txTime   = inputSize_i / UPLINK_DATA_RATE       (seconds)
    execTime = cpuDemanded_i / vruCapacity_j         (seconds)
    rxTime   = outputSize_i / DOWNLINK_DATA_RATE     (seconds)
    delay_ij = txTime + execTime + rxTime            (seconds)

  Constants:
    UPLINK_DATA_RATE   = 2500.0 KB/s  (derived from 20 MHz bandwidth)
    DOWNLINK_DATA_RATE = 2500.0 KB/s

  8.2  ENERGY CONSUMPTION
  ───────────────────────
  For task i offloaded to fog node j:
    energy_ij = (TRANSMISSION_POWER × txTime)
              + (EXECUTION_POWER × execTime)
              + (RECEIVING_POWER × rxTime)    (Joules)

  Constants:
    TRANSMISSION_POWER = 0.5 W  (device → fog)
    EXECUTION_POWER    = 1.0 W  (fog processing)
    RECEIVING_POWER    = 0.5 W  (fog → device)

  8.3  MIN-MAX NORMALIZATION
  ──────────────────────────
  Baseline (delay only):
    nd_ij = (delay_ij − minDelay) / (maxDelay − minDelay)
    normSum_ij = nd_ij

  Proposed (delay + energy, severity-weighted):
    weight = 0.5 if severity == "Minor", else 1.0
    nd_ij = ((delay_ij − minDelay) / (maxDelay − minDelay)) × weight
    ne_ij = ((energy_ij − minEnergy) / (maxEnergy − minEnergy)) × weight
    normSum_ij = nd_ij + ne_ij

  Global min/max are computed across ALL tasks × ALL fog nodes.
  If range is 0 (all values identical), range defaults to 1.0.

  8.4  URGENCY FUNCTION
  ─────────────────────
  Baseline (2 criteria):
    U(ti, fj) = w1 × 1/max(deadline_i − delay_ij, 0.5)
              + w2 × 1/pref(ti)

  Proposed (4 criteria):
    U(ti, fj) = w1 × 1/max(deadline_i − delay_ij, 0.5)
              + w2 × 1/pref(ti)
              + w3 × 1/max(energy_ij, 0.001)
              + w4 × γ(ti)

  Where:
    pref(ti) = number of fog nodes where delay_ij ≤ deadline_i
               (if 0, use 1.0 to avoid division by zero)
    γ(ti)    = 1.5 for Major tasks, 1.0 for Minor tasks
    w1..w4   = AHP-generated weights (sum to 1.0)

  Clamping:
    delayDiff is clamped to min 0.5 (prevents 1/0.001 = 1000 from
    drowning out all other terms).
    energy is clamped to min 0.001.

  8.5  AHP WEIGHT GENERATION
  ──────────────────────────
  Algorithm 3 (ACW loop):
    repeat:
      P = pmc(rand)         // Generate 4×4 pairwise matrix
      W = cwd(P)            // Column-normalise + row-average = weights
      pass = cc(P, W)       // Check consistency
    until pass OR iterations ≥ 100

  Algorithm 4 (PMC):
    v[0..3] = random in [1.0, 9.0]
    P[x][y] = getSaatyScale(v[x] / v[y])  for x < y (upper triangle)
    P[y][x] = 1 / P[x][y]                 (lower triangle)
    P[x][x] = 1.0                          (diagonal)

  Algorithm 5 (CWD):
    Column-normalise P → P_bar
    Row-average P_bar → W[0..3]   (these are the final weights)

  Algorithm 6 (CC):
    P' = P × W (element-wise: P[x][y] * W[y])
    w'[x] = rowSum(P'[x]) / W[x]
    λmax = mean(w')
    CI = (λmax − n) / (n − 1)
    RI = 0.90 (for n = 4)
    CR = CI / RI
    PASS if CR ≤ 0.1

  For 2×2 baseline: λmax = 2.0, CI = 0.0, CR = 0.0 (always passes).

  8.6  QUOTA DETERMINATION (Algorithm 1: MQD)
  ───────────────────────────────────────────
  1. Find most efficient fog node: λmax = max(vruCapacity_j)
  2. lMax = min(hMax, floor(|T| / |F|))
     where hMax = numberOfVRUs of the most efficient node
  3. For other nodes: lPrime = floor((vruCap_j / λmax) × lMax)
     minQuota_j = min(lPrime, numberOfVRUs_j)
  4. maxQuota_j = numberOfVRUs_j
  Called twice: once for all tasks, once for Major tasks only.

  SECTION 10: EXPERIMENTAL SETUP
================================================================================

  Three Algorithms Compared:
    1. GPM (Greedy Placement Method) — capacity-based greedy assignment
    2. Baseline (M-DAFTO)           — Single-Type MSDA (Algorithm 9)
    3. Proposed System (Adapted 2-Type MSDA) — Severity-aware 2-Type MSDA (Algorithm 10)

  Four Task Scales: 250, 500, 1000, 2000 tasks

  Fog Nodes: 5 per scenario (randomised each iteration)

  Iterations: 10 per scenario (results are averaged to smooth randomness)

  Total Runs: 4 scenarios × 10 iterations × 3 algorithms = 120 algorithm runs

  Metrics Measured:
    - Overall Outage Probability (%)
    - Major Outage Probability (%)
    - Minor Outage Probability (%)
    - Total Offloading Delay (seconds)
    - Average Offloading Delay (seconds)
    - Major/Minor Average Delay (seconds)
    - Total Energy Consumed (Joules)
    - Task Satisfaction (%) — Eq. 20
    - FN Satisfaction (%) — Eq. 21-22
    - Gini Index (fairness)
    - Jain Fairness Index
    - Per-FN Assignment Table (MinQ, MaxQ, Major/Minor counts, Utilisation %)
    - Per-FN Delay & Energy
    - Resource Utilisation Bars
    - Traffic Load Distribution Bars

  Data Independence:
    All three algorithms start from IDENTICAL raw data (same fog nodes,
    same tasks, same delays, same energies). Deep copy ensures each
    algorithm modifies its own independent copy. This guarantees a fair
    apples-to-apples comparison.

  SECTION 12: INTERPRETATION & KEY FINDINGS
================================================================================

  12.1  CRITICAL-TASK PROTECTION
  ─────────────────────────────
  The most important result: under normal load (250–1000 tasks), the proposed
  algorithm achieves 0% Major outage — ZERO critical surgeries fail to get
  assigned. The baseline has 1–4% Major outage at the same scales.
  Under extreme overload (2000 tasks), Major outage drops from 20.46% to
  9.36% — a 54.3% reduction even when the system is saturated.

  12.3  TRADE-OFFS
  ───────────────
  - DELAY: The proposed method has slightly higher average delay than
    baseline (e.g., 12.87 vs 12.65 at 250 tasks). This is because the
    2-Type MSDA sacrifices delay-optimal placement to ensure Major tasks
    are assigned. This is an acceptable trade-off in healthcare.

  - TASK SATISFACTION: Slightly lower for proposed (e.g., 69.96% vs 71.14%
    at 250 tasks) because the severity-aware matching sometimes assigns
    tasks to their 2nd or 3rd preferred fog node to ensure Major quotas
    are met.

  - FN SATISFACTION: IMPROVED under overload (59.08% vs 50.22% at 2000
    tasks) — the 2-Type system distributes tasks more effectively by
    leveraging separate Major/Minor quota tracking.

  - ENERGY: Slightly higher for proposed because energy is now PART of the
    optimisation, which can redirect tasks to different fog nodes.

  12.4  GPM COMPARISON
  ───────────────────
  GPM shows 0% outage at 250–1000 tasks because it simply fills fog nodes
  greedily by capacity. However, its task satisfaction is extremely low
  (9–34%) because it ignores preferences entirely. GPM fails at 2000 tasks
  (13.15% outage) because it has no quota-based fairness mechanism.

  12.5  KEY TALKING POINTS
  ───────────────────────
  • "On average across all tested scales, our method reduced overall
    outage by approximately 80% and critical-task outage by approximately
    90% compared to the baseline."

  • "The improvement is consistent across every scale, with the algorithm
    performing especially well under normal-to-high load and still showing
    significant gains even under extreme overload."

  • "Under overload, our FN Satisfaction also improved from ~50% to ~59%,
    showing better resource utilisation through severity-aware assignment."

  • "We achieve these outage reductions while maintaining comparable task
    satisfaction and delay metrics."


================================================================================
  SECTION 13: TIME COMPLEXITY
================================================================================

  Single DA round:     O(T × F)   where T = tasks, F = fog nodes
  MSDA stages:         Bounded by T (each stage removes at least one task)
  Worst case overall:  O(T² × F)

  In practice, convergence is much faster because quota constraints limit
  the number of stages. The Modified DA in 2-Type MSDA adds constant-factor
  overhead for the three-constraint rejection per fog node per round.


================================================================================
  SECTION 14: FUTURE WORK
================================================================================

  1. DYNAMIC TASK ARRIVAL
     Current system processes tasks in batch. Real hospitals have continuous
     task arrivals. Adding online/streaming task processing would make the
     system more realistic.

  2. TASK MIGRATION
     Once assigned, tasks stay put. Allowing task migration when fog node
     loads change dynamically could improve performance.

  3. REAL-WORLD WORKLOAD TRACES
     Current evaluation uses synthetic (randomly generated) data. Testing
     with real healthcare workload traces would validate practical viability.

  4. HETEROGENEOUS DEADLINES
     Current deadline range is narrow (15–22 seconds). Testing with wider
     deadline ranges and truly time-critical tasks (sub-second) would stress
     the algorithm further.

  5. FOG-TO-FOG AND FOG-TO-CLOUD OFFLOADING
     Current model only supports device-to-fog. Adding fog-to-fog horizontal
     offloading and fog-to-cloud vertical offloading would handle overflow.

  6. MULTI-TIER SEVERITY
     Current system has 2 severity levels (Major/Minor). Extending to
     3+ levels (Critical/Major/Minor/Routine) would provide finer control.

  7. MACHINE LEARNING WEIGHT GENERATION
     AHP weights are generated randomly. Using ML to learn optimal weights
     from historical data could improve performance.
